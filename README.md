# Engram

Engram is a local repository-indexing and code-intelligence service. It exposes the resulting index through a Model Context Protocol (MCP) server named `Coder`, allowing MCP clients and coding agents to query repository structure, relationships, source context, and change impact.

The project is an analysis and context layer. It does not edit source files, run a project's build commands, or replace a compiler, type checker, test runner, or human review. It can update its own index and, when enabled, add an Engram-managed block to a target repository's `AGENTS.md`.

## What It Provides

Engram can:

- Scan local repositories and maintain incremental or full indexes.
- Extract files, source chunks, symbols, imports, calls, references, includes, inheritance, properties, API calls, route relationships, and frontend field reads.
- Store relational metadata, graph relationships, and optional vector embeddings locally.
- Resolve files, symbols, qualified names, and symbol UIDs before deeper analysis.
- Search indexed code by natural-language task or concept.
- Trace callers, callees, dependencies, execution flows, data-flow paths, and shortest graph paths.
- Map API routes to handlers, frontend consumers, response fields, and response-shape checks where the relevant patterns can be detected.
- Analyze Git working-tree changes, estimate downstream impact, identify risk signals, and suggest relevant tests.
- Identify circular dependencies, likely dead code, duplicate code, likely test-coverage gaps, high-degree graph nodes, and functional communities.
- Index multiple repositories and build cross-repository group views.
- Reindex in the background or watch a repository for changes and trigger incremental indexing.
- Explain Python and TypeScript/JavaScript stack traces using indexed symbols and source context.

Results are intended to give an MCP client structured evidence for its next action. They are not guarantees of correctness; inferred relationships and framework-specific extraction can be incomplete.

## How It Works

An index run follows this general path:

1. The scanner walks a repository and applies built-in exclusions, `.gitignore` patterns, and optional include/exclude configuration.
2. Language and project parsers extract symbols and source metadata. Parser-specific relationships are added where supported.
3. Source is divided into searchable chunks. Embeddings are generated by the configured local or remote embedding provider.
4. Relational records are written to DuckDB and graph relationships are written to KuzuDB.
5. Process/flow records, review data, and index-run metrics are persisted when their features are enabled.
6. The MCP server opens the repository's manifest and exposes tools that query the local stores.

The default data directory is `data/` in the indexed repository:

- DuckDB stores files, symbols, chunks, processes, review records, communities, and index-run metadata.
- KuzuDB stores symbol and file relationships such as `CALLS`, `IMPORTS`, `INCLUDES`, `FETCHES`, and `READS_FIELD`.
- LanceDB stores vector-search records; the embedding cache is kept alongside it.
- A manifest records index readiness, counts, versions, embedding runtime information, and warnings.

Core indexing and graph storage are local by default. A remote embedding provider or optional LLM-backed review/summarization can make outbound requests; the default local embedding model may also require a one-time download on first use.

## MCP Server

The server uses the MCP stdio transport through FastMCP. Start it with `scripts/run_mcp.py` and point an MCP client at the script and the repository to analyze.

Most tools accept an optional `repo` path or indexed repository name. The server can resolve several indexed repositories, but `select_repo` only resolves a repository and returns its manifest; it does not change the server's startup default. Pass `repo` explicitly on subsequent calls when targeting a different repository.

The `reindex_project` tool defaults to background mode and returns a job ID. Use `reindex_status` to poll the job rather than holding an MCP request open for a long index run.

### Tool Groups

The registered MCP tools are grouped below by purpose.

#### Repository and Index Lifecycle

`index_status`, `index_health`, `list_repos`, `select_repo`, `reindex_project`, `reindex_status`, `get_recent_runs`, `get_run_metrics`, and `check_stale_index`.

#### Code Discovery and Context

`semantic_code_search`, `investigate_codebase`, `feature_context`, `app_context`, `resolve_target`, `find_symbols`, `get_file_summary`, `get_source_context`, `get_review_history`, `diff_context`, and `explain_error`.

#### Symbols and Graph Analysis

`unified_context`, `get_symbol_context`, `get_callers_and_callees`, `get_dependencies`, `get_file_dependencies`, `get_graph_neighborhood`, `graph_query`, `impact_analysis`, `shortest_path`, `trace_data_flow`, `preview_rename`, `find_similar_functions`, and `god_nodes`.

#### API, Routes, and Execution Flows

`route_map`, `api_impact`, `shape_check`, `field_impact`, `trace_processes`, `list_processes`, and `symbol_process_participation`.

#### Git, Change, and Test Analysis

`detect_changes`, `change_impact_report`, `pr_impact`, `post_change_review`, `find_tests_for_target`, `suggest_tests_for_change`, and `test_impact`.

#### Code-Quality and Structural Analysis

`detect_circular_dependencies`, `detect_dead_code`, `detect_duplicate_code`, `test_coverage_gaps`, `detect_communities`, `list_communities`, `get_community_detail`, and `get_symbol_community`.

#### Multi-Repository and Realtime Indexing

`group_create`, `group_add_repo`, `group_remove_repo`, `group_list`, `group_detail`, `group_sync`, `group_query`, `group_status`, `build_unified_graph`, `start_realtime_indexing`, `stop_realtime_indexing`, and `realtime_indexing_status`.

### Response Behavior

MCP responses commonly include:

- `status`
- `confidence`
- `warnings`
- `partial`
- `repo_root` and `repo_name`
- `compact_summary`
- `top_files` and `top_symbols`
- `next_tools`
- `summary_text` and `highlights`

Broad and expensive queries are intentionally bounded to protect the stdio transport and MCP client. A response may be marked partial and include warnings when traversal, source retrieval, or process analysis was capped.

## Supported Languages and Project Files

The implementation has dedicated or parser-specific support for:

- Python
- TypeScript, TSX, JavaScript, and JSX
- C and C++
- C#
- Object Pascal and common Delphi/Lazarus project files

The scanner and generic parser also recognize additional languages and file types, including Ruby, Go, Rust, PHP, Swift, Kotlin, Scala, Dart, Lua, R, Objective-C, Elixir, Erlang, F#, Visual Basic, shell scripts, PowerShell, SQL, HTML, CSS, SCSS, Vue, and Svelte. For these languages, extraction is generally heuristic rather than compiler-accurate.

Native and embedded project support includes first-pass detection of:

- `compile_commands.json`
- CMake and Make project markers
- Visual Studio `.sln` and `.vcxproj` files
- MPLAB project and workspace files such as `.mcp`, `.mcw`, `.mptags`, `.scl`, and `.plt`
- Include directories, compiler flags, targets, and device/project hints when available

C/C++ analysis is more precise when `compile_commands.json` and a usable Clang runtime are available. MPLAB support is project-file-aware; it is not a Microchip compiler or simulator.

## Representative Workflows

The following examples show the intended sequence of MCP calls. The exact invocation syntax depends on the MCP client.

### Locate an Implementation

```text
investigate_codebase(question="Where is authentication handled?")
feature_context(feature="authentication")
get_source_context(target="AuthenticationService")
```

Use `semantic_code_search` when the target is not yet known. Use `resolve_target` before graph-heavy calls when a name may be ambiguous.

### Inspect a Symbol and Its Dependencies

```text
resolve_target(target="OrderService")
get_symbol_context(target="OrderService")
get_callers_and_callees(target="OrderService")
get_dependencies(target="OrderService")
```

### Review an API Change

```text
route_map(route="/api/orders")
api_impact(route="/api/orders")
shape_check(route="/api/orders")
field_impact(route="/api/orders", field="items[].status")
```

These tools connect route handlers with detected frontend consumers and field reads when those relationships are visible to the parsers.

### Review a Working Tree Before a Commit

```text
detect_changes(scope="unstaged")
change_impact_report(scope="unstaged")
suggest_tests_for_change(scope="unstaged")
test_impact(scope="unstaged")
```

`post_change_review` combines change detection, impact analysis, test recommendations, and a stale-index check in one request.

### Inspect a Native Header

```text
index_health()
get_dependencies(target="include/common.h")
detect_changes(scope="unstaged")
```

For C/C++ and embedded projects, review the reported confidence and build-context warnings before relying on the dependency or impact results.

## Installation

### Requirements

- Python 3.11 or newer
- Local filesystem access to the repositories being indexed
- Git for Git-aware change and pull-request analysis
- Sufficient disk space for the local databases and embedding cache

The CI workflow runs on Ubuntu with Python 3.11. Windows is also supported and is a primary development environment for the project. C/C++ parsing can use the installed `libclang` package when the runtime is available.

### Setup

From the project root:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e .
Copy-Item .env.example .env
```

On POSIX shells, use the equivalent activation and copy commands:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
cp .env.example .env
```

The core indexer does not require an API key. The default embedding provider is local. A local embedding model may be downloaded on first use.

## Quick Start

1. Create an index for the repository you want Engram to analyze:

   ```powershell
   python scripts/run_index.py C:\path\to\repository incremental
   ```

   Use `full` instead of `incremental` for a complete rebuild:

   ```powershell
   python scripts/run_index.py C:\path\to\repository full
   ```

2. Start the MCP server for that repository:

   ```powershell
   python scripts/run_mcp.py C:\path\to\repository
   ```

3. Configure the MCP client to launch the same Python environment and script. A generic stdio configuration has this shape; client-specific configuration keys may differ:

   ```json
   {
     "mcpServers": {
       "engram": {
         "command": "/absolute/path/to/Engram/.venv/bin/python",
         "args": [
           "/absolute/path/to/Engram/scripts/run_mcp.py",
           "/absolute/path/to/repository"
         ]
       }
     }
   }
   ```

   On Windows, replace `command` with the path to `.venv\\Scripts\\python.exe` and use Windows paths in `args`.

## Configuration

Configuration is read from environment variables. `.env.example` contains the complete list. Common settings include:

- `CODER_PROJECT_ROOT`: repository root used when the MCP server is started without a path argument.
- `CODER_SCAN_EXCLUDED_DIRS`, `CODER_SCAN_INCLUDE_PATTERNS`, and `CODER_SCAN_EXCLUDE_PATTERNS`: adjust scanning scope.
- `CODER_EMBED_PROVIDER`, `CODER_EMBED_MODEL`, `CODER_EMBED_DEVICE`, `CODER_EMBED_API_KEY`, and `CODER_EMBED_BASE_URL`: configure local or OpenAI-compatible embeddings.
- `CODER_PROCESS_EXTRACTION_ENABLED`: enable or disable bounded execution-flow extraction.
- `CODER_REVIEW_ENABLED`: enable or disable the indexing review stage. It is `false` by default.
- `CODER_LLM_FEATURES_ENABLED`: enable optional LLM-backed review analysis and run summaries. It is `false` by default.
- `CODER_REVIEW_ANALYSIS_PROVIDER`: select `heuristic-multi-agent` or `openrouter-multi-agent` when the corresponding feature is enabled.
- `OPENROUTER_API_KEY`: required for OpenRouter-backed review analysis and summaries.
- `CODER_AGENTS_FILE_ENABLED`: control whether Engram updates its managed block in the indexed repository's `AGENTS.md`.
- `CODER_AUTO_REINDEX`: set to `1`, `true`, or `yes` to start the realtime watcher when the MCP server starts.

LLM features are disabled by default. The default review provider is deterministic and heuristic-based. Enabling an LLM provider sends review context to that provider; do not enable it for repositories that must remain fully local unless the provider is configured accordingly. Keep `.env` files and API keys out of version control.

## Realtime Indexing

The standalone watcher monitors a repository and runs incremental indexing after changes settle:

```powershell
python scripts/run_realtime_index.py C:\path\to\repository --debounce 2 --poll-interval 2
```

The MCP tools `start_realtime_indexing`, `stop_realtime_indexing`, and `realtime_indexing_status` provide the same functionality from an MCP client. The watcher uses `watchdog` with a polling fallback.

## Development and Verification

Install the development tools used by CI, then run:

```powershell
python -m pytest tests/ --tb=short -q
ruff check .
mypy --ignore-missing-imports app config indexing mcp_server models services storage
```

```powershell

```

The repository also includes `scripts/smoke_all_tools.py` for exercising the registered tool handlers against a local index.

## Repository Layout

- `app/`: index-run coordination and lifecycle
- `config/`: environment loading and runtime defaults
- `indexing/`: scanner, parsers, chunking, embeddings, native build context, and graph construction
- `mcp_server/`: MCP transport, session state, project resolution, tool registration, schemas, and formatters
- `models/`: shared data models
- `reviewers/`: heuristic and optional provider-backed review logic
- `services/`: discovery, graph, API, route, change, test, process, and code-quality services
- `storage/`: DuckDB, KuzuDB, LanceDB, manifests, and repositories
- `scripts/`: indexer, MCP server, watcher, and smoke-test entry points
- `tests/`: unit, integration, and regression tests
- `docs/`: implementation handoff notes and engineering constraints

## Limitations and Expected Failure Modes

- Engram is not a compiler, type checker, build system, or test runner.
- Graph edges may be source-extracted, inferred by heuristics, or ambiguous. Review confidence and warnings before using them to make high-risk changes.
- C/C++ analysis is strongest with compiler metadata such as `compile_commands.json`; without it, project files and heuristics provide lower-confidence context.
- MPLAB support identifies project structure and risk-sensitive files but does not emulate the Microchip toolchain.
- Dynamic dispatch, reflection, generated code, macro-heavy code, aliases, and highly abstracted frontend/API clients can reduce recall or precision.
- Generic language support provides file/chunk indexing and heuristic symbols, not full language semantics.
- Vector search depends on a working embedding backend. If the model is unavailable, semantic search can be degraded even when relational and graph tools remain usable.
- Broad graph, process, and change queries are capped. Partial output is expected for large repositories or large working trees.
- A repository must be reindexed before new source changes or newly added indexer behavior appear in its persisted MCP results.
- An already-running MCP process must be restarted after changing the MCP server code.
- LLM-backed analysis and summaries are optional and disabled by default.
